# Resale-Watcher

盯着**日本二手平台**上的关键词（RTX 5090、4090 之类），把**符合你价格区间又不是坑货**的商品挑出来、记下来，并持续跟踪它们降价还是卖掉了。

无需登录、无需浏览器。

## 数据源

| 源 | key | 接口 | 在售检索 | 成交检索 |
|---|---|---|---|---|
| メルカリ | `mercari` | JSON API（DPoP ES256 签名） | `STATUS_ON_SALE` | `STATUS_SOLD_OUT` |
| Yahoo!フリマ | `yahoo_flea` | JSON API（裸 GET，无需签名） | `itemStatus=open` | `itemStatus=sold` |
| ヤフオク | `yahoo_auction` | **HTML**（`data-auction-*` 属性） | 搜索页 | ✗ 不做，见下 |

**三边是互相独立的商品池**，必须都搜。实测同一关键词「RTX 5090」：

| 源 | 在售 | 命中 |
|---|---|---|
| メルカリ | 188 | 1 |
| Yahoo!フリマ | 108 | 7 |
| ヤフオク | 47 | 2 |

Mercari 只有 1 件——**只盯 Mercari 会漏掉九成**。

### ヤフオク 是拍卖，和另外两个不一样

它有一口价、起拍价、结束时间、出价数。判「价格合适」用的是**当前价**，
但当前价只在此刻成立——所以面板上会同时显示出价数和剩余时间：

```
¥858,000  市价110%
🔨 竞价中 · 已 10 次出价 · 当前价还会涨 · 剩 1 天 3 小时
```

不把这行摆出来，「命中」两个字就是在误导人。

**它的成交价刻意不做。** 落札相場页（`closedsearch`）没有 `data-auction-*` 属性，
只有构建哈希 class（`gv-Carousel__item--SaTobYP4YqSQeAzPrIGF` 这种，前端一发版就变）。
为多一个市价样本源去扛一个每次发版就坏的解析器不划算——ヤフオク 的商品
用另外两个源合并出来的中位数判捡漏，一样能用。

> **ヤフオク 是三个源里唯一靠解析 HTML 的**，也是最可能哪天悄悄坏掉的一处。
> 所以 `tests/test_yahoo_auction.py` 那 12 条用例比别的更要紧——
> 「搜到 0 件」和「真的没货」在日志里长得一模一样，靠测试才分得出来。

每条规则可以指定搜哪些源（规则表的 `sources` 列，留空＝全部）。
**各源独立计时、独立限速、独立退避**——一个被限流不影响另一个。

> 加新源＝在 `sources/` 下写一个 `Source` 子类，实现 `search` / `detail` / `item_url`，
> 然后在 `sources/__init__.py` 登记一行。限速、退避、熔断、每日保险丝都在基类里，不用重写。

## 说明

个人自用的比价/监控工具，只读取三个平台**对匿名访客公开的搜索结果**，不登录、不下单、不改动对方任何数据。
抓取节奏刻意保守（全局串行、请求间随机 3〜8 秒、指数退避、每日总量上限），
默认配置下三个源加起来一天约 1500 次请求。**请不要把这些值调激进。**

本项目与 メルカリ、Yahoo!フリマ、ヤフオク 及其运营方没有任何关联，
相关名称与商标归各自所有者。用它之前请自行确认符合各平台的利用规约。

## 装起来

需要 Python 3.12+ 和一个 MySQL 8+（能建库建表的账号）。

```bash
git clone <本仓库> && cd Resale-Watcher
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt

cp .env.example .env && vi .env      # 填数据库连接
./run.sh initdb                      # 建库建表
./run.sh seed                        # 写入两条起步规则（RTX 5090 / 4090）
./run.sh start                       # 启动 → http://127.0.0.1:2334
```

规则建好后先跑一轮看看：`./run.sh once`。第一轮会把三个源的在售商品全扫一遍，
按默认节奏（请求间隔 3〜8 秒）大约要几分钟。

> **抓取节奏是刻意保守的**：全局串行、绝不并发、请求间随机 3〜8 秒、
> 429/403 指数退避、每日请求总量有上限。请求量随规则数走：4 条规则 × 3 个源实测
> 每天 3000〜4000 次。请不要把这些值调激进——对面是别人的服务器。

```
./run.sh start          # 启动（面板 http://127.0.0.1:2334）
./run.sh status         # 看状态
./run.sh logs           # 看日志
./run.sh stop
```

## 一、它是怎么判断「合适」的

三层漏斗。**能在前一层用零成本干掉的，绝不留到下一层**：

每个数据源各自跑一遍这个漏斗：

```
某个源搜索「RTX 5090」返回 N 件在售（Mercari 188 / Yahoo!フリマ 108 / ヤフオク 47）
  │
  ├─ 第 1 层  标题必含词不匹配        → 直接丢弃，不入库
  │           （实测 86 件：电源线、DP 线、显卡支架、TITAN V…
  │             Mercari 的搜索是模糊的，会返回标题里压根没有 5090 的东西）
  │
  ├─ 第 2 层  标题排除词 / 价格区间 / 品相 / Shops
  │           → 入库但标 matched=0，并记下 reject_reason
  │           （留痕是刻意的：价格超区间的明天可能降价，
  │             而且你按 reject_reason 一分组就能看出自己有没有误杀好货）
  │
  └─ 第 3 层  对通过前两层的少数候选，拉一次商品详情读描述
              → 描述警示词命中就打个黄标，【但商品照样留在命中列表里】
              （「ジャンク」「異音」这类雷经常只写在描述里，
                但描述词做否决的误杀风险太大，见下面的坑 2）
```

**第 3 层为什么只标记、不否决**——这是整个设计里最重要的一条取舍：

> **误杀是沉默的**：被毙掉的商品不会出现在任何列表里，你永远不会知道错过了什么。
> **漏筛是可见的**：带黄标进来的坏货，你扫一眼就跳过了。
>
> 命中列表平时只有个位数，多几件根本不是负担，而少一件你就再也看不见了。

第 3 层每轮只有个位数请求，因为前两层已经把 188 件砍到个位数了。

扫完所有源之后，再做两件**跨源**的事（都是纯 CPU，零请求）：

- **重判**：用当前规则把这条规则名下**所有源**的商品重判一遍。
  所以你在面板上删掉一个排除词，下一轮那些被它误杀的商品就自己回到命中列表了。
- **算捡漏**：用**跨源合并**的成交中位数给命中商品标百分比。
  市价是「这东西值多少钱」，和它挂在哪个网站无关；合并样本量更大也更稳。

## 二、怎么调规则（这一节是本项目的核心）

规则表在面板「规则」页，或者数据库 `watch_rule` 表。每列都带中文注释，
用 Navicat / DBeaver 直接看也能看懂。

### 词表会自动归一化，不用穷举变体

匹配前会做：**NFKC → 小写 → 删掉所有空格和符号**。所以：

| 你填 | 能命中 |
|---|---|
| `5090` | `RTX 5090` / `RTX5090` / `ＲＴＸ５０９０` / `rtx-5090` / `GeForce　RTX　5090` |
| `ジャンク` | `ジャンク` / `ｼﾞｬﾝｸ` |

### 加规则之前先看请求预算

`daily_request_limit` 是保险丝：当天超了就**所有规则所有源一起停**到次日 0 点（JST）。
它拦的是失控循环，真正决定「对人家客气不客气」的是 `req_delay_min/max`（默认 3〜8 秒），
那两个不要动。

**估算时别只算搜索页数。** 2026-09-13 实测 4 条规则（单卡×2 每 7 分钟 + 整机×2 每 30 分钟）：

| | 次/小时 | 全天 |
|---|---|---|
| 搜索（按实测页数算） | 106 | 2540 |
| **实测总量** | **157** | **3770** |

差出来的 50 次/小时是**售出对账**——每轮要对「库里还标在售、这轮却没扫到」的商品
逐个拉详情核实是不是卖掉了。这是持续开销，不是启动突发。
所以拿页数公式估完，**再乘以 1.5** 才接近真实值。

### 整机规则：怎么把「定制接单」和笔记本挡掉

盯整机（不是裸卡）时，光靠「5090 + PC」会捞进三类假货，各有各的判据：

| 混进来的 | 例子 | 怎么挡 |
|---|---|---|
| **定制接单** | 『カスタムゲーミングPC』ご相談受付中！RTX5060Ti/5070/5080/5090搭載など | `ご相談`/`受付中`/`オーダー`/`カスタム`/`変更可能` |
| **拿本型号当性能对比** | RTX**5070Ti** 16GB(**4090**/4080/5080に近い性能) | 排除**别的显卡型号** |
| **笔记本** | GALLERIA UL9C-R49 ゲーミングPC **13900HX** 4090 | `ノート`/`インチ`/`18型` + **移动 CPU 后缀** |

后两条是这套词表里最有用的两个技巧：

- **「别的显卡型号」当排除词**。一台真 5090 整机的标题不会同时出现 4080/5070；
  会并列一串型号的，要么是接单配置器，要么是把你要的型号只写在括号里做性能对比。
- **移动 CPU 后缀 `H`/`HX`**。桌面 CPU 是 `K`/`KF`/`X`/`X3D` 结尾，笔记本是 `H`/`HX`。
  上表那条标题写着「ゲーミングPC」、没有「ノート」两个字，只有 `13900HX` 暴露了它是笔记本。

`include_any` 填的是 **CPU 型号 + PC 词**：整机必然写出其中之一，而裸卡和配件不会——
所以不用再去排除「显卡单品」，它们自己就过不了这一层。

> ⚠ 别把 `PC` 单独当匹配词：归一化会把 `PCI-E 5.0` 变成 `pcie50`，里面就含 `pc`，
> 一整批转接线和延长线会全部命中。要用 `ゲーミングpc`/`デスクトップ`/`パソコン` 这种长词。

### 三个实测踩过的坑

这三个坑都是真金白银试出来的，改词表前先看一眼：

**坑 1：整机和笔记本靠品牌名列举不完**

`Razer Blade 18 / RTX 4090/32GB/2TB` 曾经混进命中列表——Razer、ThinkPad、DAIV、
Alienware、GALLERIA、Legion、Predator… 永远列不完。

**更可靠的是侧面信号**，现在的排除词表就是围绕这个建的：

- **CPU 型号**（`ryzen` `ultra9` `14900` `9950x` `275hx`…）：整机和笔记本必写 CPU，单卡标题绝不会出现
- **存储容量**（`1TB` `2TB` `512GB` `SSD`）：显卡标的是显存（24GB/32GB），永远不会出现 TB 和 SSD
- **屏幕尺寸**（`インチ`）：单卡不标英寸

**坑 2：描述里的词多半是「否认」，拿它做否决会误杀好卡**

两块 ¥48万 / ¥50万 的好卡曾被 `マイニング` 毙掉过，因为描述里写着：

> 「マイニング**等の負荷が高い用途では使用しておらず**」＝「**没有**用于挖矿等高负荷用途」

**真挖过矿的卖家不会自招**（那等于砸自己的价），只有想自证清白的才会主动提这个词。
所以「マイニング」做否决词根本拦不到真矿卡，只会误杀良心卖家。
实测印证：读过的描述里警示词只被触发过 2 次，**2 次都是否认**。

这就是第 3 层只打标签、不否决的原因。

> **曾经为此做过一套日语否定词表 + 逐句切分，后来砍掉了。**
> 理由：标签本来就只是「你来看一眼」，误挂一个的代价是你多扫一眼，
> 而那套逻辑要额外维护一份否定词表、还要处理句子边界——不值当。
> 现在「マイニング使用しておらず」照样会挂标签。
>
> **嫌某个词的标签太吵，直接去规则页把它从 `warn_desc` 里删掉。**
> 比如「マイニング」在描述里几乎总是以否认形式出现，留着它标签会很密。

**坑 3：不能拿在售挂单当行情基准**

| | RTX 5090 单卡 |
|---|---|
| 近 30 天**成交**中位数 | **¥720,000** |
| 在售**挂单**最低要价 | ¥1,010,000 |

挂高价的卖不掉、一直挂着，所以在售列表严重高估行情。
`deal_ratio`（捡漏线）算的是**成交**中位数，不是挂单价。

### 全局设置也在面板里，不在代码里

面板「**设置**」页（数据库 `app_setting` 表）放的是**对所有规则生效**的全局项：
市价样本窗口 `median_window_days` / `median_min_samples`、请求间隔 `req_delay_min/max`、
翻页上限 `max_pages`、成交轮间隔 `sold_scan_hours`、详情预算 `detail_budget`、
消失宽限 `missing_grace_min`、每日请求上限 `daily_request_limit`、
推送 `notify_url` / `notify_body` / `notify_on` / `notify_max_per_round`。

每一项在表里和面板上都带中文说明，改完 10 秒生效，不用重启。

`.env` 里只剩改了**必须重启**的两样：数据库连接、Web 端口。

### 追踪：盯住几件，让它们更新得比别的快

平时商品的价格和状态只在**整轮关键词扫描**时更新——每条规则的 `quick_min`（默认 7 分钟），
而且一轮要遍历所有源，跑满可能好几分钟。盯一件快要结束的拍卖时，这个延迟是不够用的。

在「命中」页点商品图**右上角那颗星**（☆ → ★），它就会被**单独拉详情页刷新**：

- 价格、是否卖掉、发货地
- **出价数** —— 只有这条路能及时拿到，而那恰恰是你盯一件拍卖的理由

追踪中的商品在「**追踪**」页，那一页每行都标着上次刷新时间，因为这一页的卖点就是数据新。
星在那边是实心琥珀色，再点一下就取消——**实心/空心本身就能看出状态**，不必靠颜色分辨。

**卖掉或下架的会自动摘掉追踪**，不用你手动清。它不会丢，照常出现在「成交」页；
日志里也会点名：`追踪中的「X」卖掉了 ¥Y —— 已自动取消追踪`。

> 这个「摘」写在 `store.set_status` 和 `store.update_tracked` 里，不是写在调用方 ——
> 把状态改成终态的路径有两条（poller 里 6 个调用点走前者，追踪刷新自己写后者），
> 放到调用方去摘迟早漏掉一条，而漏掉的表现是「有商品永远摘不掉」。
> 追踪的件数是「每天多烧多少请求」的分母，挂着死货会让追踪页顶上那个估算失真。

> **这是全项目唯一按件发请求的功能。** 追 10 件、间隔 5 分钟 ＝ 每天 2880 次，
> 比四条规则的总量还大，而 `daily_request_limit` 一满是**所有规则所有源一起停**。
> 所以有两道闸：`track_min` 控间隔、`track_budget` 控每轮件数（超了就按「最久没刷新的
> 优先」轮着来，不会饿死谁，只是每件实际间隔变长）。追踪页顶上实时显示满负荷请求量，
> 加之前先看一眼那个数。

判到点用的是 `last_seen_at`（最后一次拿到新数据的时间），不另开一列——
这样**刚被整轮扫过的商品不会立刻再被单独拉一次**，搜索结果里已经有价格和状态了，
再发一个请求纯属浪费。

### 手动捡漏价：百分比判不动的时候用它

捡漏默认按「成交中位数 × `deal_ratio`%」判，但那套有个硬前提：**先得有中位数**，
而中位数要先攒够成交样本。两种情况下它整个不工作：

- 规则刚建，成交样本还没攒够
- 某个型号本来就成交稀少，永远攒不够

还有更常见的一种——**挂单价系统性高于成交价**。实测 RTX 5090：
成交中位 ¥785,000、百分比线 ¥706,500，而在售最低才 ¥869,000。
百分比线**永远不可能被碰到**，捡漏徽标一次都不会亮。

所以规则里多了一个 `deal_price`：**低于它就算捡漏，填了就完全盖过百分比**。
它不依赖任何成交样本，你心里的价就是价。

改的地方有两处：规则页的编辑框，以及**命中页每条规则顶上直接改**——
一边看着在售列表一边调价，改完立刻重算，不用等下一轮。
（那一栏放在「当前没有符合条件的商品」之上，因为一件都没命中时正是你最想调它的时候。）

> 摘要行会如实显示当前生效的是哪一个：填了手动价就显示「手动捡漏价 ¥X」，
> 不再显示百分比线，免得你对着一个不生效的数字纳闷。

### 成交页：别只看中位数那一个数字

命中页回答「现在有什么能买」，靠的是拿在售价和成交中位数比。但中位数是**一个数字**，
看不出它底下的分布——是十几件挤在同一个价位，还是从 ¥40 万到 ¥90 万拉了一条长线。
定价前要看的是后者，所以「**成交**」单开一栏。

两类数据粒度不同，都摆出来：

| | 来源 | 有什么 | 量 |
|---|---|---|---|
| **跟到成交** | `item.status='sold_out'` | 标题、缩略图、**降了多少才卖掉**、发货地 | 少 |
| **成交价样本** | `sold_sample` | 只有价格和时间，**不在页面上单列**，只用来算中位数和价格区间 | 多 |

「跟到成交」要走完**一直在跟 → 从搜索结果消失 → 对账确认售出**这条链路才会进来，
所以量少但信息最全。其中「从 ¥X 降了 ¥Y 才卖掉」是定价最直接的参考：
挂多少没人要、降到多少成交。

带「曾是捡漏」标的是**你错过的**——它在售时低于捡漏线，而且确实有人接。

### 卖家黑名单：命中页点一下就拉黑

某个店铺反复挂高价货刷屏时，在命中页那一行点「**拉黑卖家**」，
这条规则下他的全部商品**立刻**判为不合适（`reject_reason=seller`），不用等下一轮。

- **两个页面都能拉黑**。命中页在每行的品相那一行；「**全部**」页多了一列「卖家」，
  按钮三态：`拉黑` 可点 / `已拉黑` 该卖家已在这条规则的黑名单里 / `—` 这件商品没有卖家ID。
  「全部」页可以同时列出多条规则的商品，**按钮只对该行自己那条规则生效**，提示里会点名是哪条。
- **不用手抄 ID**。按钮知道是谁；规则页的 `exclude_sellers` 里也能直接编辑。
- **每条规则各自一份**，和其它词表一致。同一个卖家要在多条规则里分别拉黑。
- **拉黑不删数据**，只是判成不合适。从 `exclude_sellers` 里删掉 ID，
  下一轮那些商品就自己回到命中列表了。
- **メルカリShops 按店铺拉黑**。Shops 商品的卖家是店铺实体不是用户，接口在
  `sellerId` 位置一律返回哨兵 `"0"`，真正的标识在 `shop.id`。拉黑一次就屏蔽这家店的全部商品。
- **卖家ID 未知的商品一律放行**。ヤフオク 有一部分商品确实不给卖家ID。
  不知道 ≠ 命中 —— 和品相白名单同一个道理。

> 三个源的卖家ID 互不通用也互不重复：Mercari 是纯数字、Yahoo!フリマ 是 `p`+数字、
> ヤフオク 是 28〜29 位混合大小写串。匹配大小写不敏感。

### 推送：面板是用来复盘的，抓现货得靠推送

本项目自己的数据就是这个功能的理由：RTX 5090 成交中位数 ¥78 万，在售最低 ¥93 万——
**¥26 万〜93 万这一整段在售是空的**。好价的卡挂出来就被买走了，
它从来没在面板上停留到你下次打开的那一刻。

所以在「设置」页填上 `notify_url` 就会开始推送，**留空＝完全关闭，一个请求都不发**。

不接某一家的 SDK，就是一个 URL 加一个请求体模板，常见的几家都能用：

| 服务 | `notify_url` | `notify_body` |
|---|---|---|
| ntfy | `https://ntfy.sh/你的主题` | 留空 |
| Bark | `https://api.day.app/你的KEY` | 留空 |
| Discord | webhook 地址 | `{"content": "{text}"}` |
| 企业微信 | 群机器人 webhook | `{"msgtype":"text","text":{"content":"{text}"}}` |
| Telegram | `https://api.telegram.org/bot<TOKEN>/sendMessage` | `{"chat_id":"你的id","text":"{text}"}` |

`{text}` 是提醒正文，填进 JSON 时会自动转义——日文商品名里的引号不会把模板撑破。

推出去长这样（价格在第一行——手机通知栏只看得见前两行，决定要不要点开的那个数必须在里面）：

```
🟢 捡漏 ¥350,000 · 市价的 81% | RTX 4090 单卡
MSI GeForce RTX 4090 VENTUS 3X E 24G OC 3ファン搭載 グラフィックスボード
中位 ¥427,800
🔨 拍卖 · 已 1 次出价 · 还会涨 · 剩 3 小时（09-15 20:58 截止）
https://page.auctions.yahoo.co.jp/jp/auction/xxxxxxxxx
```

手动捡漏价判出来的写「低于手动线 ¥950,000」而不是「市价的 114%」——那两个并排看着自相矛盾。

同一件商品可能收到三种头：

| 头 | 什么时候 | 设置 |
|---|---|---|
| 🟢 捡漏 / 命中 | 它刚够格那一刻，每件一次 | `notify_on` |
| 📉 再降 | 推过之后比**上次推送时的价格**又跌够 N% | `notify_redrop_pct`，默认 0＝关 |
| ⏰ 捡漏快结束 | 拍卖进入最后 N 分钟、价格还在捡漏线内 | `notify_final_min`，默认 60 |

在命中页**剔除**的商品不再推送（含快结束提醒）——剔掉就是"别再拿它烦我"。

两个默认值是刻意的：

- **只推捡漏**（`notify_on=deal`）。命中只是「符合你的条件」，捡漏才是「该立刻去看」。
  所有命中都推的话，一条规则几十件在售会让你一天之内把推送关掉。要全推就改成 `matched`。
- **一轮最多 5 条**（`notify_max_per_round`），**超了就一条都不推、全部标成已推**。
  挡的是三种一次性井喷：刚填上 URL（库里几十件老命中一起轰出来）、停机几天后重启
  （攒下的过期货）、放宽规则或改价格区间（几百件同时变命中）。
  代价是真有一波好货时会被整批跳过，但那种情况面板上看得到；被几十条通知淹掉的人
  只会直接把推送关了。

还有一条要知道：**发送失败不重试**，失败也记成已推。一条迟到一小时的提醒没有意义，
而对着挂掉的地址每轮重试会一直拖慢抓取、把日志刷满。失败会在日志里出声。

> `notify_url` 等于一把钥匙，谁拿到都能往你手机推东西。别写进截图，也别提交进仓库。
> 面板目前**没有鉴权**，所以别把它暴露到公网。

### 面板「全部」页会告诉你每一件是被哪个词判掉的

判定列旁边有一列**具体原因**，和判定逻辑读的是同一份词表和阈值，所以永远一致：

| 判定 | 具体原因 | 商品 |
|---|---|---|
| 标题排除词 | `14900、SCAR` | ROG Strix SCAR G834 i9 14900HX |
| 标题排除词 | `2TB、ノート` | DELL i7 13代 2TB RTX4090 32gb ノートPC |
| 超预算 | `¥3,500,000 ＞ 上限 ¥1,200,000` | RTX 5090 LIGHTNING Z 搭載 究極デスクトップ |
| Shops商家品 | `メルカリShops 商家出品` | 新品 CY ATX3.0 PCI-E 5.0 |
| 合适 | `⚠ 描述含：マイニング` | MSI SUPRIM Liquid X RTX 4090 |

调词表时按这一列看，就知道每个词到底在替你挡什么、有没有挡错。
**标题本身就是链接**，点一下新标签页直接开商品页
（个人出品走 `/item/xxx`，メルカリShops 走 `/shops/product/xxx`，两种路径不一样，代码里已分开处理）。

> **这一列上线当天就抓出一个真误杀**：词表里原本有 `5090D`（中国特供 D 版），
> 而归一化会把「RTX 5090 **DUAL**」变成 `rtx5090dual`，里面正好含 `5090d` ——
> ASUS DUAL 这个主流型号会被当成 D 版杀掉。D 版在日本 Mercari 实测 0 件，
> 为防一个不存在的东西误杀主流型号不划算，所以这两个词已经删了。
>
> **加新排除词时留意这类子串陷阱**：把词往真实型号名里套一遍再决定。
> 已知安全的反例见 `tests/test_matcher.py::test_排除词不能误杀ASUS_DUAL`。

### 改完词表先重放，别等下一轮

```bash
./run.sh replay 1          # 零请求，拿库里已抓的商品重跑一遍当前规则
./run.sh replay 1 --apply  # 确认没问题再写回数据库
```

重点看输出最后那段 **「⚠ 潜在误杀」**——被标题排除词拦下、
但价格正好落在你预算区间里的商品，并列出每件命中了哪个词。
真正的误杀只会出现在这里（价格不合适的本来你也不会买）。

> **误杀是沉默的**：商品不会出现在任何列表里，你永远不会知道错过了什么。
> 加宽排除词最多多几条噪音，你一眼能看见；加狠了就再也看不见了。宁松勿紧。

## 二点五、面板是暗色的

`ui.dark_mode(True)` 强制暗色，主色 blue-400 / 负色 red-400，用 oklch 指定（P3 屏上不走 sRGB 夹紧）。

除了开暗色，还修了 Quasar 在暗底上的两处短板——**两处都是"写死白字"引起的**：

| 处 | Quasar 默认 | 改成 |
|---|---|---|
| 徽标 `.q-badge{color:#fff}` | amber 底上白字 **1.67:1**、green 2.28:1 | 亮底配深字 → 7~10:1 |

### 设计语言（加新界面时照抄，别再发明）

改完之前这里是散的：8 种按钮写法、3 种卡片间距、说明文字有的在按钮后有的塞在正文里，
字体族干脆没指定。都收敛成了 `web/ui.py` 顶上的几个常量：

| 常量 | 用在哪 |
|---|---|
| `BTN_PRIMARY` | 主操作：一键抓取、保存、新建规则 |
| `BTN_GHOST` | 次操作：设置规则、编辑、立即跑一轮 |
| `BTN_QUIET` | 轻操作：刷新、取消 |
| `BTN_DANGER` / `BTN_DANGER_SOLID` | 拉黑、删除 / 删除确认框 |
| `INPUT` | 所有输入框、下拉框 |
| `CARD` | 所有卡片和折叠块的外边距 |
| `BADGE_LABEL` | 描边徽标 |

**字体**：必须显式指定字体族。不指定的话日文用什么字全看浏览器挑——同一页里
商品标题（日文）和界面文案（中文）会落到两套字形上，笔画粗细和字面大小对不齐。
现在按操作系统各自的系统字排（macOS 走 SF Pro + ヒラギノ，Windows 走 Segoe + 游ゴシック）。

**等宽数字**（`font-variant-numeric: tabular-nums`）：这是个盯价格的工具，
一整列 ¥ 数字不等宽的话，位数不同的价格左右横跳，扫一眼比大小要重新对焦。
只影响阿拉伯数字，汉字假名不受影响。

**徽标分两类**，这是这套界面里最重要的一条视觉规则：

- **信号**（实心）：捡漏、已降、新上架、東京都、描述警示——回答「要不要点进去」
- **标签**（描边 `BADGE_LABEL`）：来源、数据源——只回答「它是什么」

一行里五六个实心色块会互相抢，真正的信号反而沉下去。所以来源改成了描边。

**卡片底部那行**（拉黑卖家 → 品相 → 发货地 → 上架时间）固定四项、贴底对齐
（正文列 `self-stretch` + 该行 `mt-auto`）。宽屏两列时同一行两张卡片高度取决于高的那张，
不贴底的话矮的那张这行会悬在半空。**别往这行里加东西**——会变的信息一律做成徽标放标题上方。

> 改 `ui.notify` 时注意：**必须写驼峰 `textColor`**。NiceGUI 只把 `close_button` / `multi_line`
> 转成驼峰，其余原样下发给 Quasar——写成 `text_color` 会被静默忽略，看起来改了、实际没有。

## 三、轮询节奏与风控

实测「RTX 5090」全网在售只有 **188 件，2 页就扫完**，所以每轮都是全量扫描——
新上架、降价、售出一次全抓到，不需要分快轮慢轮。

| 项 | 值 | 说明 |
|---|---|---|
| 扫描间隔 | 7 分钟（规则表 `quick_min`，实际抖动 ±20%） | 每条规则独立 |
| 请求间隔 | 随机 3〜8 秒（设置页 `req_delay_min/max`） | 全局串行，绝不并发 |
| 单轮请求数 | 2 次搜索 + 0〜10 次详情（`detail_budget`） | 稳态个位数 |
| 成交轮 | 24 小时一次（`sold_scan_hours`），≤5 页（`max_pages`） | 算市价中位数；搜到的已售出商品，库里还标在售的直接改状态 |
| 同关键词复用 | 另一条规则 `search_reuse_min`（默认 5）分钟内翻过的同关键词页直接复用 | 单卡/整机关键词相同，整机那份不再重翻；一条规则不复用自己上一轮的 |
| 交易中的商品 | `trading_recheck_min`（默认 180）分钟核实一次 | 它不出现在在售搜索里，按 20 分钟对账等于每天白拉上百次 |
| 每日上限 | 3000 次（设置页 `daily_request_limit`） | 超了当天**所有规则所有源**一起停抓 |
| 遇到 429/403 | 退避 60s → 120s → 300s 封顶，连续失败开熔断 | 被限流时真的睡着不动 |
| メルカリ 详情回 403 | 正文带 `InvisibleItemException` ＝ **商品已删除**，按 404 处理、不退避 | 这不是限流；当限流处理过一次，一件删掉的商品堵死整个源的对账三天 |

**实测**默认配置（2 条规则 × 3 个源 × `quick_min=7`）约 **2000 次/天**，
已经占掉 3000 上限的三分之二。估算公式：

```
requests/day ≈ 规则数 × Σ各源页数 × (1440 / quick_min) + 详情与成交轮
```

**所以加第三条规则、或把 `quick_min` 从 7 调到 5，都会当天撞线。** 动这两个值之前
先把 `daily_request_limit` 一起调大。

**售出对账有个前提**：只有当次扫描**扫全了**（没被 `MAX_PAGES` 截断）才做。
没扫全的时候「商品没出现」不等于「卖掉了」，硬判会把一堆在售商品错标成已售出。
被截断时日志里会明确告警，面板规则页也会显示 ⚠（想扫全就到设置页调大 `max_pages`）。

## 四、数据表

库名默认 `resale_watcher`，在 `.env` 的 `DB_NAME` 里改。

| 表 | 干什么 |
|---|---|
| `watch_rule` | **你自己填的规则**：关键词、**数据源**、词表、**卖家黑名单**、价格区间、品相、捡漏线、扫描间隔 |
| `rule_state` | 每条规则的市价中位数（跨源合并算） |
| `rule_source_state` | 每条规则**在每个源上**的轮询进度、在售总数、是否被截断、最近报错 |
| `item` | 抓到的商品 + 判定结果。主键 `(source, item_id, rule_id)`。`desc_warn` 是描述警示标签（**不参与** `matched`）；`end_time`/`bid_count`/`buy_now_price` 是拍卖三件套，只有 ヤフオク 会填满；`notified_at` 记推送过没有（失败也记，不重试） |
| `price_log` | 价格变动历史（只在价格真的变了时写一行） |
| `sold_sample` | 成交价样本。`source` 是哪个网站，`sample_kind` 是怎么收集到的（`scan`＝成交轮扫的、只过了标题级规则；`tracked`＝我们一路跟到成交的，拉过详情最准） |
| `daily_stat` | 每日请求计数（**按源**分开记，便于排查是哪个源在烧请求）。上限管的是全源合计 |
| `app_setting` | **你自己填的全局设置**：市价样本窗口、抓取节奏、详情预算、每日上限、推送地址。每行都带 `note` 说明 |

时间列一律由 Python 按 **Asia/Tokyo** 写入，不用 `DEFAULT CURRENT_TIMESTAMP`——
数据库、开发机、部署机三边时区不保证一致。

**改表结构不用删库**：往 `db/schema.sql` 里加一列、改一句 `COMMENT`、或者把
`VARCHAR(24)` 加宽成 `VARCHAR(32)`，下次启动都会自动同步到已有的库上
（`db/store.py` 的 `sync_schema`，注释和类型都会比）。
反过来**只增不删**——库里有而 `schema.sql` 里没有的列一律原样留着，
自动 DROP 一列就是不可逆地删数据。

## 五点五、两台机器一起跑、以及卡死了怎么办

- **多实例只有一份在抓。** 本机和 NAS 共用一个库时，靠 `poller_lease` 表里的租约决定谁抓：
  拿到租约的那份抓，其余待命（顶栏会写「待命：轮询由 X 执行」）。持有者每扫完一个源续一次期；
  它卡死或关机，`poller_lease_sec`（默认 600 秒）到期后待命的那份自动接手。
  正常退出（`./run.sh stop`）会主动放掉租约，下一个进程立刻能接。
  `poller_lease_sec=0` 关掉租约，回到各抓各的。
- **数据库连接带超时。** 2026-09-15 一次网络抖动让轮询线程在一条半开的 MySQL 连接上
  卡了 40 小时——进程活着、面板开着、顶栏红字，但没人看面板。现在 `.env` 里
  `DB_CONNECT_TIMEOUT / DB_READ_TIMEOUT / DB_WRITE_TIMEOUT`（默认 10/30/30 秒）保证卡不住。
- **看门狗会推到手机。** 心跳停超过 `poller_stall_min`（默认 10 分钟）就往 `notify_url` 推一条
  「轮询已停 N 分钟」，每个停机段一次，6 小时不恢复再提醒一次。
- 顶栏：配额用完显示「⏸ 今日请求已到上限，0 点自动恢复」（不用重启）；
  轮询停了显示停了多久、心跳停在几号几点。
