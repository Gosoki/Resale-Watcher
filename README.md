# Resale-Watcher

盯着**日本二手平台**上的关键词（RTX 5090、4090 之类），把**符合你价格区间又不是坑货**的商品挑出来、记下来，并持续跟踪它们降价还是卖掉了。

无需登录、无需浏览器。

## 数据源

| 源 | key | 接口 | 在售检索 | 成交检索 |
|---|---|---|---|---|
| メルカリ | `mercari` | JSON API（DPoP ES256 签名） | `STATUS_ON_SALE` | `STATUS_SOLD_OUT` |
| Yahoo!フリマ | `yahoo_flea` | JSON API（裸 GET，无需签名） | `itemStatus=open` | `itemStatus=sold` |
| ヤフオク | `yahoo_auction` | **HTML**（`data-auction-*` 属性） | 搜索页 | ✗ 不做，见下 |

**三边是互相独立的商品池**，必须都搜。实测同一关键词「RTX 5090」：

| 源 | 在售 | 命中 |
|---|---|---|
| メルカリ | 188 | 1 |
| Yahoo!フリマ | 108 | 7 |
| ヤフオク | 47 | 2 |

Mercari 只有 1 件——**只盯 Mercari 会漏掉九成**。

### ヤフオク 是拍卖，和另外两个不一样

它有一口价、起拍价、结束时间、出价数。判「价格合适」用的是**当前价**，
但当前价只在此刻成立——所以面板上会同时显示出价数和剩余时间：

```
¥858,000  市价110%
🔨 竞价中 · 已 10 次出价 · 当前价还会涨 · 剩 1 天 3 小时
```

不把这行摆出来，「命中」两个字就是在误导人。

**它的成交价刻意不做。** 落札相場页（`closedsearch`）没有 `data-auction-*` 属性，
只有构建哈希 class（`gv-Carousel__item--SaTobYP4YqSQeAzPrIGF` 这种，前端一发版就变）。
为多一个市价样本源去扛一个每次发版就坏的解析器不划算——ヤフオク 的商品
用另外两个源合并出来的中位数判捡漏，一样能用。

> **ヤフオク 是三个源里唯一靠解析 HTML 的**，也是最可能哪天悄悄坏掉的一处。
> 所以 `tests/test_yahoo_auction.py` 那 12 条用例比别的更要紧——
> 「搜到 0 件」和「真的没货」在日志里长得一模一样，靠测试才分得出来。

每条规则可以指定搜哪些源（规则表的 `sources` 列，留空＝全部）。
**各源独立计时、独立限速、独立退避**——一个被限流不影响另一个。

> 加新源＝在 `sources/` 下写一个 `Source` 子类，实现 `search` / `detail` / `item_url`，
> 然后在 `sources/__init__.py` 登记一行。限速、退避、熔断、每日保险丝都在基类里，不用重写。

## 说明

个人自用的比价/监控工具，只读取三个平台**对匿名访客公开的搜索结果**，不登录、不下单、不改动对方任何数据。
抓取节奏刻意保守（全局串行、请求间随机 3〜8 秒、指数退避、每日总量上限），
默认配置下三个源加起来一天约 1500 次请求。**请不要把这些值调激进。**

本项目与 メルカリ、Yahoo!フリマ、ヤフオク 及其运营方没有任何关联，
相关名称与商标归各自所有者。用它之前请自行确认符合各平台的利用规约。

## 装起来

需要 Python 3.12+ 和一个 MySQL 8+（能建库建表的账号）。

```bash
git clone <本仓库> && cd Resale-Watcher
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt

cp .env.example .env && vi .env      # 填数据库连接
./run.sh initdb                      # 建库建表
./run.sh seed                        # 写入两条起步规则（RTX 5090 / 4090）
./run.sh start                       # 启动 → http://127.0.0.1:2334
```

规则建好后先跑一轮看看：`./run.sh once`。第一轮会把三个源的在售商品全扫一遍，
按默认节奏（请求间隔 3〜8 秒）大约要几分钟。

> **抓取节奏是刻意保守的**：全局串行、绝不并发、请求间随机 3〜8 秒、
> 429/403 指数退避、每日请求总量有上限。默认配置下三个源加起来一天约 1500 次请求，
> 平均每 60 秒一次。请不要把这些值调激进——对面是别人的服务器。

```
./run.sh start          # 启动（面板 http://127.0.0.1:2334）
./run.sh status         # 看状态
./run.sh logs           # 看日志
./run.sh stop
```

## 一、它是怎么判断「合适」的

三层漏斗。**能在前一层用零成本干掉的，绝不留到下一层**：

每个数据源各自跑一遍这个漏斗：

```
某个源搜索「RTX 5090」返回 N 件在售（Mercari 188 / Yahoo!フリマ 108 / ヤフオク 47）
  │
  ├─ 第 1 层  标题必含词不匹配        → 直接丢弃，不入库
  │           （实测 86 件：电源线、DP 线、显卡支架、TITAN V…
  │             Mercari 的搜索是模糊的，会返回标题里压根没有 5090 的东西）
  │
  ├─ 第 2 层  标题排除词 / 价格区间 / 品相 / Shops
  │           → 入库但标 matched=0，并记下 reject_reason
  │           （留痕是刻意的：价格超区间的明天可能降价，
  │             而且你按 reject_reason 一分组就能看出自己有没有误杀好货）
  │
  └─ 第 3 层  对通过前两层的少数候选，拉一次商品详情读描述
              → 描述警示词命中就打个黄标，【但商品照样留在命中列表里】
              （「ジャンク」「異音」这类雷经常只写在描述里，
                但描述词做否决的误杀风险太大，见下面的坑 2）
```

**第 3 层为什么只标记、不否决**——这是整个设计里最重要的一条取舍：

> **误杀是沉默的**：被毙掉的商品不会出现在任何列表里，你永远不会知道错过了什么。
> **漏筛是可见的**：带黄标进来的坏货，你扫一眼就跳过了。
>
> 命中列表平时只有个位数，多几件根本不是负担，而少一件你就再也看不见了。

第 3 层每轮只有个位数请求，因为前两层已经把 188 件砍到个位数了。

扫完所有源之后，再做两件**跨源**的事（都是纯 CPU，零请求）：

- **重判**：用当前规则把这条规则名下**所有源**的商品重判一遍。
  所以你在面板上删掉一个排除词，下一轮那些被它误杀的商品就自己回到命中列表了。
- **算捡漏**：用**跨源合并**的成交中位数给命中商品标百分比。
  市价是「这东西值多少钱」，和它挂在哪个网站无关；合并样本量更大也更稳。

## 二、怎么调规则（这一节是本项目的核心）

规则表在面板「规则」页，或者数据库 `watch_rule` 表。每列都带中文注释，
用 Navicat / DBeaver 直接看也能看懂。

### 词表会自动归一化，不用穷举变体

匹配前会做：**NFKC → 小写 → 删掉所有空格和符号**。所以：

| 你填 | 能命中 |
|---|---|
| `5090` | `RTX 5090` / `RTX5090` / `ＲＴＸ５０９０` / `rtx-5090` / `GeForce　RTX　5090` |
| `ジャンク` | `ジャンク` / `ｼﾞｬﾝｸ` |

### 三个实测踩过的坑

这三个坑都是真金白银试出来的，改词表前先看一眼：

**坑 1：整机和笔记本靠品牌名列举不完**

`Razer Blade 18 / RTX 4090/32GB/2TB` 曾经混进命中列表——Razer、ThinkPad、DAIV、
Alienware、GALLERIA、Legion、Predator… 永远列不完。

**更可靠的是侧面信号**，现在的排除词表就是围绕这个建的：

- **CPU 型号**（`ryzen` `ultra9` `14900` `9950x` `275hx`…）：整机和笔记本必写 CPU，单卡标题绝不会出现
- **存储容量**（`1TB` `2TB` `512GB` `SSD`）：显卡标的是显存（24GB/32GB），永远不会出现 TB 和 SSD
- **屏幕尺寸**（`インチ`）：单卡不标英寸

**坑 2：描述里的词多半是「否认」，拿它做否决会误杀好卡**

两块 ¥48万 / ¥50万 的好卡曾被 `マイニング` 毙掉过，因为描述里写着：

> 「マイニング**等の負荷が高い用途では使用しておらず**」＝「**没有**用于挖矿等高负荷用途」

**真挖过矿的卖家不会自招**（那等于砸自己的价），只有想自证清白的才会主动提这个词。
所以「マイニング」做否决词根本拦不到真矿卡，只会误杀良心卖家。
实测印证：读过的描述里警示词只被触发过 2 次，**2 次都是否认**。

这就是第 3 层只打标签、不否决的原因。

> **曾经为此做过一套日语否定词表 + 逐句切分，后来砍掉了。**
> 理由：标签本来就只是「你来看一眼」，误挂一个的代价是你多扫一眼，
> 而那套逻辑要额外维护一份否定词表、还要处理句子边界——不值当。
> 现在「マイニング使用しておらず」照样会挂标签。
>
> **嫌某个词的标签太吵，直接去规则页把它从 `warn_desc` 里删掉。**
> 比如「マイニング」在描述里几乎总是以否认形式出现，留着它标签会很密。

**坑 3：不能拿在售挂单当行情基准**

| | RTX 5090 单卡 |
|---|---|
| 近 30 天**成交**中位数 | **¥720,000** |
| 在售**挂单**最低要价 | ¥1,010,000 |

挂高价的卖不掉、一直挂着，所以在售列表严重高估行情。
`deal_ratio`（捡漏线）算的是**成交**中位数，不是挂单价。

### 全局设置也在面板里，不在代码里

面板「**设置**」页（数据库 `app_setting` 表）放的是**对所有规则生效**的全局项：
市价样本窗口 `median_window_days` / `median_min_samples`、请求间隔 `req_delay_min/max`、
翻页上限 `max_pages`、成交轮间隔 `sold_scan_hours`、详情预算 `detail_budget`、
消失宽限 `missing_grace_min`、每日请求上限 `daily_request_limit`。

每一项在表里和面板上都带中文说明，改完 10 秒生效，不用重启。

`.env` 里只剩改了**必须重启**的两样：数据库连接、Web 端口。

### 面板「全部」页会告诉你每一件是被哪个词判掉的

判定列旁边有一列**具体原因**，和判定逻辑读的是同一份词表和阈值，所以永远一致：

| 判定 | 具体原因 | 商品 |
|---|---|---|
| 标题排除词 | `14900、SCAR` | ROG Strix SCAR G834 i9 14900HX |
| 标题排除词 | `2TB、ノート` | DELL i7 13代 2TB RTX4090 32gb ノートPC |
| 超预算 | `¥3,500,000 ＞ 上限 ¥1,200,000` | RTX 5090 LIGHTNING Z 搭載 究極デスクトップ |
| Shops商家品 | `メルカリShops 商家出品` | 新品 CY ATX3.0 PCI-E 5.0 |
| 合适 | `⚠ 描述含：マイニング` | MSI SUPRIM Liquid X RTX 4090 |

调词表时按这一列看，就知道每个词到底在替你挡什么、有没有挡错。
**标题本身就是链接**，点一下新标签页直接开商品页
（个人出品走 `/item/xxx`，メルカリShops 走 `/shops/product/xxx`，两种路径不一样，代码里已分开处理）。

> **这一列上线当天就抓出一个真误杀**：词表里原本有 `5090D`（中国特供 D 版），
> 而归一化会把「RTX 5090 **DUAL**」变成 `rtx5090dual`，里面正好含 `5090d` ——
> ASUS DUAL 这个主流型号会被当成 D 版杀掉。D 版在日本 Mercari 实测 0 件，
> 为防一个不存在的东西误杀主流型号不划算，所以这两个词已经删了。
>
> **加新排除词时留意这类子串陷阱**：把词往真实型号名里套一遍再决定。
> 已知安全的反例见 `tests/test_matcher.py::test_排除词不能误杀ASUS_DUAL`。

### 改完词表先重放，别等下一轮

```bash
./run.sh replay 1          # 零请求，拿库里已抓的商品重跑一遍当前规则
./run.sh replay 1 --apply  # 确认没问题再写回数据库
```

重点看输出最后那段 **「⚠ 潜在误杀」**——被标题排除词拦下、
但价格正好落在你预算区间里的商品，并列出每件命中了哪个词。
真正的误杀只会出现在这里（价格不合适的本来你也不会买）。

> **误杀是沉默的**：商品不会出现在任何列表里，你永远不会知道错过了什么。
> 加宽排除词最多多几条噪音，你一眼能看见；加狠了就再也看不见了。宁松勿紧。

## 二点五、面板是暗色的

`ui.dark_mode(True)` 强制暗色，主色 blue-400 / 负色 red-400，用 oklch 指定（P3 屏上不走 sRGB 夹紧）。

除了开暗色，还修了 Quasar 在暗底上的两处短板——**两处都是"写死白字"引起的**：

| 处 | Quasar 默认 | 改成 |
|---|---|---|
| 徽标 `.q-badge{color:#fff}` | amber 底上白字 **1.67:1**、green 2.28:1 | 亮底配深字 → 7~10:1 |
| 通知条 `type=warning/positive/…` | warning 底上白字 **1.70:1** | 同上 → 6.4~10.4:1 |

卡片和表格的投影也去掉了（暗底上投影看不见、只会糊），换成 `rgba(255,255,255,.08)` 的淡描边分层。
文字色整体从亮底的 -600/-700 档提到 -400 档，在 `#121212` 上都在 6.7:1 以上。

> 改 `ui.notify` 时注意：**必须写驼峰 `textColor`**。NiceGUI 只把 `close_button` / `multi_line`
> 转成驼峰，其余原样下发给 Quasar——写成 `text_color` 会被静默忽略，看起来改了、实际没有。

## 三、轮询节奏与风控

实测「RTX 5090」全网在售只有 **188 件，2 页就扫完**，所以每轮都是全量扫描——
新上架、降价、售出一次全抓到，不需要分快轮慢轮。

| 项 | 值 | 说明 |
|---|---|---|
| 扫描间隔 | 7 分钟（规则表 `quick_min`，实际抖动 ±20%） | 每条规则独立 |
| 请求间隔 | 随机 3〜8 秒（设置页 `req_delay_min/max`） | 全局串行，绝不并发 |
| 单轮请求数 | 2 次搜索 + 0〜10 次详情（`detail_budget`） | 稳态个位数 |
| 成交轮 | 24 小时一次（`sold_scan_hours`），≤5 页（`max_pages`） | 算市价中位数 |
| 每日上限 | 3000 次（设置页 `daily_request_limit`） | 超了当天停抓 |
| 遇到 429/403 | 退避 60s → 120s → 300s 封顶，连续失败开熔断 | 被限流时真的睡着不动 |

按默认节奏两条规则一天约 400〜500 次请求，平均每 3 分钟一次。

**售出对账有个前提**：只有当次扫描**扫全了**（没被 `MAX_PAGES` 截断）才做。
没扫全的时候「商品没出现」不等于「卖掉了」，硬判会把一堆在售商品错标成已售出。
被截断时日志里会明确告警，面板规则页也会显示 ⚠（想扫全就到设置页调大 `max_pages`）。

## 四、数据表

库名默认 `resale_watcher`，在 `.env` 的 `DB_NAME` 里改。

| 表 | 干什么 |
|---|---|
| `watch_rule` | **你自己填的规则**：关键词、**数据源**、词表、价格区间、品相、捡漏线、扫描间隔 |
| `rule_state` | 每条规则的市价中位数（跨源合并算） |
| `rule_source_state` | 每条规则**在每个源上**的轮询进度、在售总数、是否被截断、最近报错 |
| `item` | 抓到的商品 + 判定结果。主键 `(source, item_id, rule_id)`。`desc_warn` 是描述警示标签（**不参与** `matched`）；`end_time`/`bid_count`/`buy_now_price` 是拍卖三件套，只有 ヤフオク 会填满 |
| `price_log` | 价格变动历史（只在价格真的变了时写一行） |
| `sold_sample` | 成交价样本。`source` 是哪个网站，`sample_kind` 是怎么收集到的（`scan`＝成交轮扫的、只过了标题级规则；`tracked`＝我们一路跟到成交的，拉过详情最准） |
| `daily_stat` | 每日请求计数（**按源**分开记，便于排查是哪个源在烧请求）。上限管的是全源合计 |
| `app_setting` | **你自己填的全局设置**：市价样本窗口、抓取节奏、详情预算、每日上限。每行都带 `note` 说明 |

时间列一律由 Python 按 **Asia/Tokyo** 写入，不用 `DEFAULT CURRENT_TIMESTAMP`——
数据库、开发机、部署机三边时区不保证一致。

## 五、命令

```bash
./run.sh start|stop|restart|status|logs|fg
./run.sh seed              # 写入两条起步规则（RTX 5090 / 4090），幂等
./run.sh once [规则ID]      # 立刻跑一轮就退出，不启面板
./run.sh replay [规则ID]    # 零请求重放，改完词表用它验证
./run.sh test              # 回归测试（43 条，零网络）：匹配逻辑 + ヤフオク HTML 解析
./run.sh initdb            # 建表（start 时会自动建）
```

`tests/` 里的用例全部是实测从 Mercari 真实返回的商品，改 `normalize.py`
或 `matcher.py` 之后**必须**先跑一遍——那是这个项目唯一能挡住「改一处、坏另一处」的东西。

## 六、部署到 NAS

```bash
git pull && bash deploy.sh     # root 运行
```

装 uv → 建 venv → 验证能连上 MySQL → 生成 systemd 服务并启动。幂等，可反复跑。

会把 `WEB_HOST` 改成 `0.0.0.0`。**面板本身无鉴权**，局域网内谁都能改你的监控规则；
真要暴露到不可信网络，在 NAS 的反向代理上加一层 Basic Auth。

## 七、目录

```
config.py          .env 里的结构项（连库、端口）+ SETTINGS_SPEC（全局设置的类型/默认值/说明）
main.py            入口：轮询线程 + NiceGUI 面板，一个进程
core/normalize.py  文本归一化（全半角、大小写、空格、半角片假名）
core/matcher.py    规则匹配 + 描述警示标签 + 捡漏判定
sources/base.py    数据源抽象 + 公共的请求纪律（限速、退避、熔断、每日保险丝）
```
