## 二、已经改了（3 个 commit）

### 1. ヤフオク 滤掉混进来的 Yahoo!フリマ 商品　`ceda547`

ヤフオク 的搜索结果里混着 `isflea=1` 的 フリマ 商品，而 フリマ 我们有独立源在抓。
不滤掉就是同一件商品进两个源：面板显示两遍、成交样本记两次把中位数带偏。

实测：当前默认排序恰好一件都不返回，所以**今天滤不滤结果一样**；
但加上 `&s1=new&o1=d` 立刻混进来——RTX 5090 从 47 件变 91 件，
多出的 44 件全是 `isflea=1`。也就是说今天的干净只靠 Yahoo 默认排序的
一个隐含前提撑着，对方改个默认值我们就会静默开始重复计数。

### 2. schema.sql 新增的列能同步到已有库　`faea642`

原先只同步**列注释**，往 `schema.sql` 加一列对已有库毫无作用——
代码 SELECT 它就报 Unknown column，出路只剩手写 ALTER 或删库重建。
而重建会丢掉攒了几天的成交样本，也就是市价中位数的全部依据。

拆了纯函数 `plan_schema_changes` 以便离线测，并锁死**只增不删**：
库里有而 `schema.sql` 里没有的列一律不动。

### ✅ 4. 卖家黑名单 —— 你已拍板，2026-09-12 做完

做的过程里顺带挖出四个真问题（都已修，见下）：

1. **`revalidate` 的 SELECT 漏 `seller_id`** —— 扫描判成不合适、重判又放回来，

4. **`insert_rule` 对缺失的列传 `None`** —— 每往 `watch_rule` 加一个 NOT NULL 新列，
   `tools/seed.py` 这种手写字典的调用方就当场 IntegrityError。改成只插
   `data` 里真有的列，缺的走 DDL 默认值（`update_rule` 一直就是这么做的）。
